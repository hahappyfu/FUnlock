## 〇、执行规则与红线（必读）

### 编码阶梯（ponytail:full，浓缩版）

按序停在第一个站得住的台阶：
1. 该存在吗——投机需求不做，一句话说明即可（YAGNI）
2. 仓库已有同类实现 → 复用
3. 标准库 → 用
4. 平台原生特性 → 用
5. 已装依赖 → 用，不为几行代码新增依赖
6. 一行能写 → 一行
7. 都不行 → 最小可工作实现

纪律：
- bug 修根因：在所有调用方共经的共享函数改一处，不给每个调用点打补丁
- 不写：单实现接口/抽象、单产品工厂、永不变化的配置项、「以后用」的脚手架占位；删除优于添加；少文件；短 diff；平实优于取巧
- 故意留下的已知天花板简化，标 `ponytail:` 注释写明天花板与升级路径（如 `// ponytail: 全局锁，吞吐上来改按账号分锁`）
- 不简化：信任边界的输入校验、防数据丢失的错误处理、安全、无障碍、用户明确要求的东西
- 非平凡逻辑（分支/循环/解析/钱与安全路径）留一个最小可运行检查（assert 自检或一个小测试）；trivial 一行逻辑不用留
- 汇报：代码优先，说明 ≤3 行（跳过了什么、何时需要补）

### 项目红线

1. **代码签名**：必须真实 Apple Development 证书签名（TEAM JJYCS98SHK）。**禁止 ad-hoc**——TCC 辅助功能/定位权限与签名哈希绑定，ad-hoc 覆盖会导致权限随哈希变动失效。
2. **测试套件可安全运行**：破坏性用例已于 2026-09-28 修复（全量 444 用例），可放心跑 `xcodebuild test`。
3. **只动必须动的**：每个问题独立提交（commitlint conventional 格式，中文描述），不顺手"改善"旁边代码；只清理自己造成的孤儿。

## 一、问题清单（按优先级）

### P1-1 呼吸动画空转：弹窗关闭后动画不停，CPU 15~21% 永久空转【双审确认，正在发生】

- **现象**：当前进程 CPU 21.3% 且持续上涨（累计 CPU 时间与"首次展开弹窗后按 15-19% 空转"精确吻合）；`sample PID` 可见 RepeatAnimation.animate / NSHostingView.layout / CA::Transaction::commit 高频重绘。触发条件：**点开过一次状态栏弹窗**（10-02 11:08:54 之后永久空转；此前 41 小时 0%）。
- **根因**：b41341d 把 `statusDot` 的 `repeatForever` 呼吸动画启停绑定在 SwiftUI `onAppear/onDisappear`（`FUnlock/MenuBarPopover.swift:26,93-99,256-263`）。但状态栏 NSPopover 是 `.transient` 行为（`AppDelegate.swift:551`）且**未实现 NSPopoverDelegate**：点击外部关闭时 AppKit 仅 orderOut，contentViewController 常驻、视图不脱离，SwiftUI 的 onDisappear 永不触发，动画永不停止。
- **为什么是 P1**：唯一正在消耗电量的进行时缺陷；Debug 构建（-Onone）下放大更明显。

### P1-2 入侵告警 100% 误报：22/22 次手动解锁均触发 intruded【双审确认】

- **现象**：修复后窗口内 22 次手动输密码解锁（含大量手表紧贴电脑、RSSI -48~-66 场景）全部在 2.04~2.33 秒后触发 intruded 事件（events.log）。
- **根因**：`FUnlock/FUnManager+Events.swift:118-129` 的入侵判定只有两个条件：`!wasFUnUnlock`（不是 FUn 自动解锁）+ `unlockRSSI != UNLOCK_DISABLED`（功能开启），**没有任何设备在场/RSSI 判定**。上轮 P1-2 修复只解决了"FUn 自己的自动解锁被误标"，从未实现"手动解锁时区分设备在不在场"。
- **当前影响**：无系统通知（只写 events.log + 用户脚本钩子），但一旦用户为 intruded 配了脚本（AutomationView 支持自定义脚本），每次手动输密码都会误触发告警。

### P1-3 显示器熄灭场景首注失败：固定 300ms 等待不足，失败率 28%【双审确认】

- **现象**：试运行窗口 7/25 次解锁首注失败（全部"第 1/3 次尝试"）。序列一致：`isDisplayPoweredOn: IOEnginePower not found`（显示器熄灭）→ sendShiftKey 成功 → **固定等 300ms** → 注入 posted=true → 双验证超时 → fail。其中 3 次用户 1.7-8.9 秒后放弃等待手动输密码（每次叠加一次 P1-2 的 intruded 误报）。
- **根因**：`FUnlock/SystemInteractionService.swift:332` 硬编码 `Task.sleep(nanoseconds: 300_000_000)`；显示器从熄灭到 loginwindow 密码框就绪超过 300ms，首注落入空窗。

### P1-4 瞬时注入失败误报 axRevoked + 模态警告弹窗【双审确认】

- **现象**：09-30 11:57:11 一次注入 Level1（cgSessionEventTap）/Level2（cghidEventTap）失败、Level3 因 "screen no longer secure" 中止，被记为 axRevoked 并可能弹出"辅助功能权限被撤销"模态警告（runModal 抢焦点）。实际是**用户手动解锁与注入赛跑**（5 秒内屏幕已 unlocked），权限完全正常。
- **根因**：`FUnlock/UnlockOrchestrator.swift:170-177` 把任何 `posted=false` 折叠为 `reason: .axRevoked` 并调用 `showAXRevokedAlertIfNeeded`（`SystemInteractionService.swift:527-545`，NSAlert.runModal）。瞬态竞态与真实权限撤销未区分。

### P2-1 预唤醒（Phase 6）结构性不可达：0 次触发【双审确认，修复分两步】

- **现象**：wakeOnProximity=1 全程开启但 `[SM] pre-wake triggered` 自 09-26 起零次。
- **根因（三重叠加）**：
  1. 显示器休眠期 BLE 采样缺口巨大：10-01 夜间窗口最大缺口 531.6s（8.86 分钟）、>5s 缺口 1784 次；10-01 白天 4.6 小时仅 60 条 RSSI、最大缺口 1.8 小时。EMA 被饿死，信号不可能爬到阈值。
  2. 阈值无提前量：`FUnSignalProcessor.swift:306-314` `preWakeThreshold = max(unlockRSSI − wakeAdvance, −100)` = −85，与 lockRSSI −85 恰好同值；`FUnManager+Events.swift:199` 注释里的"-60"已过时。
  3. 门控过窄：`FUnManager+Events.swift:200,286` 要求 `state.screen == .displaySleeping`，手动锁屏（locked(manual)）下即使屏幕黑屏也永远无法触发。
- **注意**：这是行为设计问题而非崩溃，必须**先补观测再调参**（见设计方案），禁止直接改参数。

### P2-2 单测污染生产 events.log【双审确认，根因已定位】

- **现象**：`~/Library/Application Support/FUnlock/events.log` 含 96 条 `test_default_window`（时间戳 2023-11-15 = 测试固定时钟 1_700_000_000）。每次跑全量测试都会追加 2 条。

### P2-3 诊断页时间线分块渲染以 `\.offset` 为 ID，动态追加致乱序/闪烁【Opus 发现】

## 二、修复设计方案

### D1-1 呼吸动画：NSPopoverDelegate 关停

**方案（推荐 A）**：
1. `AppDelegate` 实现 `NSPopoverDelegate`，`popover.delegate = self`（AppDelegate.swift:551 附近），实现 `popoverDidClose`：把"弹窗已关闭"状态推给 SwiftUI 视图。
2. SwiftUI 侧把 `MenuBarPopover.swift:26` 的 `@State private var popoverVisible` 改为读共享可观察对象（如 `final class PopoverVisibilityModel: ObservableObject { @Published var visible = false }` 单例，或并入现有配置单例模式），`onAppear/onDisappear` 保留作为补充信号；`syncBreathing(visible:)` 消费该状态。
3. 兜底：若验证发现某些关闭路径不触发 popoverDidClose（如系统睡眠），在 `applicationDidResignActive` 或系统睡眠通知里同样重置 visible=false。

**涉及文件**：`FUnlock/AppDelegate.swift`（popover 配置区 ~540-560 行）、`FUnlock/MenuBarPopover.swift`（26、93-99、256-263 行）。注意 b41341d 的 commit message 声称"动画启停与弹窗可见性绑定"，现有实现保留只改状态来源，不要重写动画本身。

**边界**：不改变 popover 的 .transient 行为；不改变 statusDot 视觉表现；弹窗打开期间动画必须正常运行（修好后用验收标准验证两个方向）。

### D1-2 intruded 加设备在场判定

**方案**：`FUnManager+Events.swift` onUnlock() 中，在启动 intrudeCheckTask 前**同步捕获**解锁瞬间信号快照（照抄现有 `wasFUnUnlock` 快照模式，避免 2 秒后读到变化后的值）：

```swift
let wasFUnUnlock = orchestrator.isAutoUnlockingOrRecentlyCompleted
// 新增：设备在场判定（EMA 平滑值，避免瞬时抖动误判）
let snap = fun.signalSnapshot()
let devicePresent = snap 有效 && snap.effectiveRSSI >= Double(fun.unlockRSSI)
// 2 秒后：仅"非 FUn 解锁 && 设备不在场"才告警
if !wasFUnUnlock && !devicePresent { runScript("intruded"...) ; logEvent("intruded"...) }
```

保留现有 `unlockRSSI != UNLOCK_DISABLED` 哨兵门控（解锁功能禁用时不告警）。**必须保留 B2 语义**：设备不在场时手动解锁仍报入侵。用 effectiveRSSI（EMA）而非瞬时 rssi 判断，减少"手表在口袋导致瞬时弱信号"的误告警。

**涉及文件**：`FUnlock/FUnManager+Events.swift:88-131`。若 signalSnapshot 有现成在场判断方法（查 FUnSignalProcessor/FUn 的公开属性）直接复用，不要新造。

### D1-3 首注：Shift 后轮询显示器就绪

**方案**：`SystemInteractionService.injectPasswordWithPrelude`（~332 行）把固定 300ms 改为：
1. Shift 发送成功后，轮询现有显示器电源检测（isDisplayPoweredOn，IOEnginePower 检测）直到返回 true 或超时（建议上限 3s，步进 100-200ms）。
2. 超时则照旧注入（不再延长等待）；就绪则立即注入。
3. 保留现有"注入前 isSecureToInject 检查"不变。
4. 可选加固：轮询期间若屏幕状态已变为 unlocked（用户手动解锁抢先），中止注入并返回失败原因（与 D1-4 的返回类型改造配合）。

**涉及文件**：`FUnlock/SystemInteractionService.swift`（injectPasswordWithPrelude 及 isDisplayPoweredOn）。**不要**改重试逻辑——重试是事件驱动的，没有退避参数。

### D1-4 axRevoked：区分瞬态竞态与真实撤销

**方案**：把注入结果从 Bool 细化为带原因的 enum（或最小改动：posted=false 分支内追加判定）：
1. 注入前/后调用 `AXIsProcessTrusted()`（ApplicationServices，仓库可能已在用——先 grep）。
2. `posted=false` 且 `AXIsProcessTrusted()==true` 且屏幕状态在注入期间翻转（isSecureToInject 由 true 变 false，或 m.state.screen 已非 locked）→ **瞬态竞态**：记 `recordUnlock(.skipped, reason: .axRevoked?)`——不，用新增/复用轻量 reason（如 .skipped + detail"注入竞态（用户手动解锁）"），**不弹窗**。
3. `AXIsProcessTrusted()==false` → 真实撤销：保持现有 axRevoked 记录 + 弹窗（保留 1h 节流）。

改动返回值会波及调用方（UnlockOrchestrator.swift:165 附近）与相关测试——先 grep `injectPasswordWithPrelude` 全部调用点与测试再改；若改动面大，采用"posted=false 分支内追加判定"的最小改法。

**涉及文件**：`FUnlock/SystemInteractionService.swift`、`FUnlock/UnlockOrchestrator.swift:160-180`。

### D2-1 预唤醒：先补观测，后解耦（两阶段，禁止一步到位）

**阶段 1（先做，纯观测）**：在 BLE 扫描回调管线（BLEScanner / FUn 的 RSSI 入口）记录相邻广播间隔：间隔 >30s 时 debug.log 打一条 `[BLE] scan gap Xs at <time>`；显示器休眠事件（onDisplaySleep）时记录 CoreBluetooth central.state。目的：确定休眠期停顿是 Watch 停止广播还是 Mac 扫描被系统挂起。

**阶段 2（拿到阶段 1 数据后再做）**：
- 阈值解耦：新增配置键 `preWakeRSSI`（默认 -75，UI 在概览页可填），`preWakeThreshold` 改为"有 preWakeRSSI 时直接返回该值，否则回退现公式"；**不要**动 lockRSSI 语义。
- 门控放宽（locked(manual) 熄屏态也允许预唤醒）**仅列为待议实验**——manualLockNoAutoUnlock=1 时点亮显示器可能骚扰用户，等阶段 1 数据与用户确认后再决定。

## 四、通用修复与验证流程

1. **修一项 → 单测 → 提交一项**（commitlint conventional，中文，如 `fix(intrusion): 入侵告警增加设备在场判定`），不要多问题混在一个提交。
2. **P1 批次全部修完**后统一打包装机验证：
   - 编译：`xcodebuild -project FUnlock.xcodeproj -scheme FUnlock build`（沿用现有 Debug 配置，与当前装机一致；Release 切换是另一个议题，不在本手册范围）
   - 全量测试通过。
3. **安装流程（严格按序）**：
   1. `pkill FUnlock` 并确认进程退出
   2. `zip` 打包
   3. `rm -rf /Applications/FUnlock.app`（必须先删再装）
   4. `cp -R` 安装到 /Applications
   5. `touch /Applications/FUnlock.app`
   6. `open /Applications/FUnlock.app`
4. **真机观察窗口 ≥3 天**，按 docs/dev-rules/log-driven-iteration.md 判定是否进入下一轮：样本达标（解锁事件 ≥300 或 3 个自然日）+ 日志能解释现象，才能下结论。
5. 日志位置：`~/Library/Logs/FUnlock/`（decisions.jsonl、debug.log、timing.log、shadow_telemetry.csv）+ `~/Library/Application Support/FUnlock/events.log`。
6. 每项验收用本手册 §三 的对应清单逐条打勾，验收结果写回一份简短报告（修复了什么、验收数据、遗留项）。
