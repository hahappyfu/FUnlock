## 做对了什么

1. **三层审计策略(验证→深挖→行为)而非"再扫一遍"**。上一轮刚做过全维度审计,重复扫描边际收益低;改为"验证上轮修复质量"直接命中要害——上轮修复自己引入了 3 个新缺陷(P0-1 破坏性测试是 808bb2c 新加的、P1-1 改密守卫是 B4 引入的、P0-3 手动唤醒自杀是"修复 #10"引入的)。
2. **"发现当线索不当事实"的核验纪律**。所有 agent 的 P0/P1 我都亲自读代码核验,纠正 4 处:P0-1 影响夸大(收窄到注入慢/失败窗口)、P1-3 影响夸大(僵尸 timer 有信号回升保护)、F-2 文件指错(写越层在 NetworkSettingsView 非 MainWindowView)、EMA agent 删掉了 `if let rssi` 失联守卫(总指挥补回)。不核验就会被带着走。
3. **任务书自包含 + grep/编译级验收标准**。13 个 agent 全部按验收交付,包括"用例数精确对账""数据安全前后 diff"这类硬标准。
4. **并行冲突预防**:文件所有权互斥 + pbxproj 由总指挥预登记(4 agent 并发编辑工程文件必炸)。

## 做错了什么(诚实)

1. **审计前跑了"基线"全量测试,删掉了 Debug 版真实 Keychain 密码**。顺序错了——应先审计测试套件安全性再跑。影响限于 dev 条目(正式版完好),且恰好把 P0-1 炸了出来,但这是运气不是设计。教训:**未知安全性的测试套件,先只读审计,后执行**。
2. **上一轮的教训没人吸收**:测试全绿 ≠ 行为正确。390 个通过的用例里有 28 个恒真/空转,两个"通过"的用例在删用户数据。本轮给所有修复任务书都加了"禁止空转假测试"条款才止血。
3. **任务书里的数字要实测**:拆分预估"删后 374-380"是错的(实际 366),靠逐 agent 对账才闭环。
4. **API 路由不稳定**(captcha 400)中断 3 个 agent 两轮。自包含任务书 + SendMessage 断点续跑把损失兜住了,但重派耗了额外时间。
