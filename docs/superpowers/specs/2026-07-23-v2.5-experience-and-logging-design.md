# FUnlock v2.5 设计规格：体验止抖 + 日志口径修正

## 目标

在不改动信号管道和核心安全逻辑的前提下，优先解决两类问题：

1. 短时间内 lock/unlock 事件反复跳变导致的体验抖动。
2. 事件日志与遥测日志不能准确反映“真实解锁/锁屏结果”的问题。

本版本遵循分阶段策略：

- 先止抖（体验修复）。
- 再增强日志（可观测性修复）。
- 不在本次引入大规模重构或新功能。

## 背景与现状

根据本地日志分析，当前存在以下问题：

- `events.log` 中出现短时间内连续 locked/unlocked 事件链。
- 存在 327 次 locked 后 30 秒内再次 locked 的记录。
- 存在同一秒或极短间隔内 `locked -> unlocked` 连续记录。
- `ScriptRunner.shared.logEvent("unlocked")` 在注入键盘事件后立即记录，但屏幕是否真正解锁是 2 秒后才检查。
- `shadow_telemetry.csv` 目前缺少“结果”和“解锁耗时”字段，不便于量化成功率和延迟。

## 设计原则

1. 最小改动优先：只修改必要路径，避免波及无关模块。
2. 结果导向：日志必须区分“已尝试”和“已确认”。
3. 可回退：新增逻辑默认可用开关控制，必要时可快速降级。
4. 可验证：每个改动都必须有可检查的日志指标或行为变化。

## 方案总览

### 1. 体验止抖（最小方案）

在 `FUnManager` 中新增三个控制机制：

#### 1.1 解锁冷却（Unlock Cooldown）

- 解锁成功后进入冷却窗口（建议默认 `5s`）。
- 冷却期内忽略新的自动解锁触发。
- 用途：避免刚解锁后因 BLE 信号微动再次发起注入。

#### 1.2 锁屏后首次解锁缓冲（Post-Lock Settle）

- 自动锁屏后设置短缓冲窗口（建议默认 `0.8s`）。
- 窗口内不立即发起自动解锁。
- 用途：防止锁屏和解锁在同一事件链中几乎同时触发。

#### 1.3 事件去重（Dedup Window）

- 对关键事件（`unlocked`、`locked:*`）设置 3 秒去重窗口。
- 相同类型事件在窗口内仅记录一次。
- 此规则优先应用于事件日志与用户脚本触发，不改变底层状态语义。
- 用途：减少日志噪音和脚本重复调用。

### 2. 日志口径修正

#### 2.1 区分已尝试与已确认

保留：

- `unlocked`（已注入）

新增：

- `unlock_confirmed`（屏幕确认解锁）
- `unlock_failed`（注入后仍未解锁）

#### 2.2 事件补充字段

建议在 `ScriptRunner.logEvent` 的输出中扩展字段格式：

- `event`
- `result`：`success / fail / timeout`
- `latencyMs`：从注入到确认的耗时
- `source`：`auto / user / system`
- `rssi`
- `effectiveRSSI`
- `device`

兼容策略：

- 现有 `StatsView` 和外部脚本若只读前几个字段，应保持可解析。
- 新字段追加在后，避免破坏已有消费方。

#### 2.3 TelemetryLogger 增强

在 `shadow_telemetry.csv` 中新增列：

- `Result`
- `LatencyMs`
- `InjectTime`
- `ConfirmTime`

目标：

- 可直接统计自动解锁成功率。
- 可分析解锁平均延迟。
- 可区分“密码错误”、“权限问题”、“超时未确认”等问题分布。

## 任务拆分

### 任务 1：最小冷却机制

负责角色：v2.5 实施

实施范围：

- `FUnManager.swift` 中增加 `unlockCooldown`、`postLockSettle`、`dedupWindow` 相关控制逻辑。

不改范围：

- 信号管道
- 密码读取与 Keychain 逻辑
- 系统辅助功能权限逻辑本身

验收角色：pro

验收标准：

- 解锁成功后 5 秒内不再触发新的自动解锁。
- 自动锁屏后 0.8 秒内不立即触发解锁。
- 3 秒窗口内同类事件不再重复记录。

### 任务 2：日志口径改造

负责角色：v2.5 实施

实施范围：

- 在 `FUnManager` 解锁结果确认后新增 `unlock_confirmed / unlock_failed` 写入。
- 扩展事件字段。

验收角色：pro

验收标准：

- 注入成功但未解锁不再只记录 `unlocked`。
- 日志可明确区分成功、失败、超时。

### 任务 3：TelemetryLogger 增强

负责角色：v2.5 实施

实施范围：

- `TelemetryLogger.swift` 增加结果与耗时字段。

验收角色：pro

验收标准：

- CSV 可用于成功率统计和延迟分析。

### 任务 4：回归与稳定性检查

负责角色：v2.5 实施

验收角色：pro

检查场景：

- 正常离开 -> 靠近自动解锁
- 手动锁屏后不被自动解锁误触发
- 屏保/休眠/唤醒场景
- 解锁失败后告警逻辑
- 事件日志增长与格式一致性

## 验收分级

### Critical

- 解锁冷却和缓冲机制必须生效。
- 新日志不能破坏现有关键流程。
- 不能出现“人已靠近但永远无法自动解锁”的回归。

### Important

- `unlock_confirmed / unlock_failed` 必须准确对应屏幕结果。
- Telemetry 字段必须完整、可解析。
- 事件去重不得吞掉必要的不同类事件。

### Minor

- 日志格式美化
- 默认参数可调优
- 后续可视需要开放用户设置项

## 风险与降级策略

### 风险 1：冷却过强导致正常解锁延迟

降级：

- 将冷却窗口改为可配置，默认值从保守向平衡调整。

### 风险 2：日志字段扩展影响旧脚本

降级：

- 采用“追加字段”策略，不改变原有前面字段顺序。

### 风险 3：去重窗口吞掉有效事件

降级：

- 仅对相同事件类型去重，不对跨类型事件去重。

## 成功标准

发布 v2.5 后应满足：

1. `events.log` 中 3 秒内连续重复事件显著减少。
2. `unlock_confirmed` 与 `unlock_failed` 能真实反映屏幕解锁结果。
3. `shadow_telemetry.csv` 可直接用于成功率与延迟分析。
4. 用户主观体验上明显减少“刚解锁又锁”或“反复抖动”的情况。

## 不在本次范围内

- BLE 信号管道重构
- RSSI 阈值自动调优
- 新平台功能扩展
- 大规模 UI 改版

## 附：实施与验收分工

- v2.5 负责实施。
- pro 负责验收审核。
- Critical 问题必须在发布前修复。
- Important 问题必须在继续下一阶段前修复。
- Minor 问题可记录到后续迭代。
